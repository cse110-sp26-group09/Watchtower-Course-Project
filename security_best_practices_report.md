# WatchTower security and maintainability review

## Follow-up review — October 4, 2026

The working tree was clean before this review. A **live** npm registry audit found two vulnerable development dependencies that the machine's offline npm cache did not report. Both are patched in `package-lock.json`; a subsequent live audit reports **zero advisories**, including with development dependencies. The production-only audit also reported zero advisories before the update.

### Findings fixed

10. **Moderate — public telemetry could disable a dashboard's analytics views with prototype-key values.** An event with `route: "__proto__"` made `buildLatencyByRoute` throw `TypeError: routes[route].push is not a function` (`src/backend/event-store.js:206` before the fix). Similar untrusted keys were used in the server's schema, session, error, and query grouping maps (`src/backend/server.js:448`, `:503`, `:563`, `:741`, `:991`). Because public events can be assigned to the configured demo owner, an unauthenticated sender could trigger 500 responses on that owner's stats or insights endpoints. The affected dictionaries now have null prototypes, and the incoming event copy no longer uses a prototype-bearing target (`src/backend/server.js:1111`). Regression: `tests/e2e/security-boundaries.spec.js:53`. This fixes an availability failure; no cross-tenant data disclosure or global prototype mutation was demonstrated.
11. **Moderate — individual public events could consume excessive retained storage.** The former 1 MiB request limit still allowed a single nearly 1 MiB event. With a 10,000-event retention cap, this could put substantial pressure on an in-memory instance or the database. Ingestion now rejects events over 16 KiB (`src/backend/server.js:1102`) and JSON deeper than 64 levels or more than 50,000 nodes (`src/backend/server.js:430`) before downstream traversal. Regression: `tests/e2e/security-boundaries.spec.js:20`. This may reject unusually large error stacks; SDK events observed by the existing tests remain accepted.
12. **High advisory severity, development-only — `brace-expansion`.** Jest's transitive paths originally resolved 1.1.18 and 2.1.4, both within the [reported denial-of-service advisory range](https://github.com/advisories/GHSA-q2hr-2g5m-vwhr). After integrating the Jest update from PR #208, the lockfile resolves patched 2.1.7 and 5.0.12. These packages are not imported by the production HTTP server; exploitability through an API request was not established.
13. **Moderate advisory severity, development-only — `markdown-it`.** JSDoc resolved 14.2.0, within the [reported quadratic-time linkify range](https://github.com/advisories/GHSA-253c-mchw-3w2r). The lockfile now resolves 14.3.2. The application does not render caller-supplied Markdown at runtime.

### Remaining exposure and verification

Public ingestion still has no project credential or request-rate control. A caller can submit plausible small events to the configured demo owner, and a distributed caller can consume storage or processing capacity. The 16 KiB event limit reduces per-event amplification but does not authenticate the sender. A project-key ownership design and an edge or shared-store rate limit are still needed before treating the endpoint as a multi-tenant production service. The prior review's notes about service-role database access and deployment configuration also remain applicable.

The local branch also combines the version bumps in Dependabot PRs #206–#211: `dotenv` 18.0.4, `jose` 6.2.12, Jest 30.5.2, Playwright 1.63.0, Supabase 2.117.2, and `markdown-it` 14.3.2. Supabase requires Node.js 22+, so `package.json`, `README.md`, and `docs/onboard.md` now declare Node.js 22–24; verify any higher-priority `NODE_VERSION` override in Render. These PRs remain open on GitHub until the repository connection permits their remote resolution.

Verified against the final combined lockfile with `npm ci --ignore-scripts --offline=false`, 26 unit tests, 29 browser/API tests, JSDoc generation, and a live `npm audit --offline=false --audit-level=low` with zero advisories.

## September 24 baseline review

Reviewed September 24, 2026. The line numbers below refer to that review's code snapshot. The active application is a framework-free Node.js HTTP server (`src/backend/server.js`) that serves a static HTML/CSS/JavaScript dashboard and browser SDK. Clerk provides sign-in; the backend verifies Clerk JWTs when configured. Supabase/Postgres stores events and user profiles through `@supabase/supabase-js`, with an in-memory local fallback. The external GitHub Pages demo sends telemetry to the API. Historical prototypes under `archive/` are not part of `npm start`.

The repository now installs cleanly, passes its unit and browser suites, and has **zero npm audit advisories** at the time of this review. The fixes below retain the dashboard's polling behavior and remove optional email delivery that the README described as locally validated but not deployed as a production flow.

## Confirmed security weaknesses addressed

1. **High — global unauthenticated event disclosure.** The old `GET /api/events/stream` broadcast every ingested event to every connected client without an owner check. Telemetry could include error messages, session identifiers, and user-provided data. The route and browser EventSource client were removed; the dashboard already polls owner-scoped APIs. Regression: `tests/e2e/security-boundaries.spec.js:16`.
2. **High — public telemetry could select another account's event owner.** The old ingestion logic preserved payload `userId` for unauthenticated events, including when a default demo owner was configured. That let a public sender inject events into an arbitrary user's dashboard. `src/backend/server.js:1067` now stamps the verified or configured owner and ignores public payload owner IDs on remotely reachable servers. The old ShopDemo payload bridge remains available only when the server binds to loopback for local prototype use. Regression: `tests/e2e/security-boundaries.spec.js:49`.
3. **High — production could trust a caller-supplied user header.** Without a real Clerk key, the server trusted `X-Clerk-User-Id`, and an escape hatch could enable the same behavior even with a key. `src/backend/server.js:128` now refuses production startup without verification or with the escape hatch; `src/backend/server.js:1394` binds unverified local mode to loopback. The current user sync route (`src/backend/server.js:1103`) no longer accepts `clerkUserId` from the body as an owner. The JWKS issuer must use HTTPS. Production startup rejection was verified locally.
4. **Moderate — unbounded input and expensive query abuse.** JSON bodies previously accumulated without a byte limit; a single request could consume excessive memory. `src/backend/server.js:389` caps JSON at 1 MiB, `src/backend/server.js:1067` caps event batches at 100, and `src/backend/server.js:1192` bounds developer queries and limits them to 60 per authenticated user per minute. Invalid JSON returns 400 and oversized input returns 413. Regression: `tests/e2e/security-boundaries.spec.js:20` and `:72`.
5. **Moderate — broad browser access and missing response controls.** CORS previously defaulted to `*` for private APIs. `src/backend/server.js:274` now uses explicit allowed origins, and `src/backend/server.js:1086` sets MIME sniffing, referrer, permissions, and frame-embedding headers. Static file containment uses a path-relative check (`src/backend/server.js:308`). A full script/style CSP needs a separate compatibility pass because Clerk and the existing UI load scripts dynamically.

## Dependency advisories and reachability

6. **Nodemailer 9.0.3, direct production dependency, high aggregate audit severity.** It was imported only by the optional Gmail OAuth alert mailer. The unauthenticated recipient registration route supplied addresses that could reach Nodemailer's address parser if an alert was triggered, so the [parser denial-of-service advisory](https://github.com/advisories/GHSA-2x7j-588g-ccc2) was plausibly reachable; exploitability was not demonstrated. [File/URL access bypass advisories](https://github.com/advisories/GHSA-8m3c-c648-2xjj) did not match this fixed HTML-only message path. Removing the optional mailer eliminated Nodemailer and the associated public recipient route. Historical research and changelog entries remain as records, not active instructions.
7. **`qs` 6.15.2, production transitive dependency, moderate.** Chain: `googleapis → googleapis-common → qs`. `googleapis` was used only by the deleted Gmail OAuth mailer. The application did not call `qs` on inbound API query strings, so the [reported parser paths](https://github.com/advisories/GHSA-x5fp-wj9c-mxmx) were not shown to be reachable. Removing `googleapis` removed `qs`.
8. **`js-yaml` 3.15.1, development transitive dependency, high.** Chain: `jest → @jest/core → @jest/transform → babel-plugin-istanbul → @istanbuljs/load-nyc-config → js-yaml`. It is not loaded by the production server. The lockfile now resolves 3.15.2, which is outside the [reported advisory range](https://github.com/advisories/GHSA-2883-xcg3-v3hh). No unrelated direct package was upgraded.
9. **Unused direct `pg` dependency.** The active data layer imports `@supabase/supabase-js`, not `pg` (`src/backend/event-store.js:15`, `:432`). `pg` was removed. A research note claimed it was used, but that note is a proposal rather than current runtime code.

## Remaining risks and manual work

- **Public ingestion remains open.** `POST /api/events` and `POST /api/beacon` must accept the external demo today. A malicious sender can still flood or poison the configured demo owner's data within the new per-request limits. A per-project ingestion key and owner mapping is the next substantive security change; it needs a migration plan for existing SDK clients. Avoid treating CORS as API authentication.
- **Database service-role access bypasses RLS.** The server scopes reads by Clerk user ID, but the Supabase service-role credential is broad. Keep it server-side and consider database policies or a narrower access model when project-key ingestion is designed. No destructive schema change was made.
- **Deployment configuration requires attention.** Set a valid `CLERK_PUBLISHABLE_KEY`, `NODE_ENV=production`, and a comma-separated `CORS_ALLOWED_ORIGINS` including each external SDK origin. The old Gmail variables are no longer used. A local ignored `.env` existed; its obsolete Gmail and alert keys were removed without printing their values. A tracked-file/history check found no committed `.env` or obvious hard-coded secret patterns, but this is not a credential inventory of deployment services. Rotate any credential if maintainers know it was exposed elsewhere.
- **Front-end accessibility is improved, not fully certified.** The dashboard has a skip link, stronger focus indicator, reduced-motion handling, and announced notification status; privacy dialogs now trap and restore focus. The app still contains custom `role="button"` controls and a large dynamic dashboard. Automated browser tests covered key focus behavior, but a complete screen-reader and contrast review remains useful.
- **CI supply chain:** `.github/workflows/ci.yml` has read-only permissions and versioned official actions. It still downloads a rolling `vnu.jar` and uses unpinned `npx` lint tools during CI. Pinning and checksum verification should be considered when maintainers next revise the workflow. Dependabot's weekly npm and GitHub Actions checks remain enabled.
